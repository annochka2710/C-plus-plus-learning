# Делегирование и делегаты в C++

**Делегирование** — приём, при котором объект передаёт часть своей работы
другому объекту. Он знает, когда и зачем нужна операция, а получатель
поручения знает, как её выполнить. Получатель часто называется делегатом.

Например, сервис отчётов формирует сообщение о готовности, а доставку
поручает внешнему обработчику: консольному, сетевому или сохраняющему текст.
Это позволяет менять доставку без изменения логики подготовки сообщения.

## Это паттерн или возможность языка?

Слово «делегат» используют в разных смыслах: как объект-помощник,
как callback со связанным объектом или как конкретный тип в библиотеке.
Поэтому сначала уточняй, что именно сохраняется и кто этим владеет.

Делегирование — общий приём объектного проектирования; отдельного паттерна
с именем Delegate в каталоге 23 паттернов GoF нет. Он используется
во многих паттернах, включая Strategy, State и Decorator.
В C++ нет стандартного `std::delegate` или ключевого слова `delegate`.

Сам приём не принимался в каком-то стандарте: его можно реализовать
в C++98 через композицию, ссылки и виртуальные методы. Пример в этом модуле
использует лямбды и `std::function`, поэтому требует C++11.
Делегирующие конструкторы C++11 — отдельная возможность языка.

## Участники примера

[delegate.cpp](delegate.cpp) содержит три роли:

| Участник | Ответственность |
|---|---|
| `ReportService` | Формирует сообщение и решает, когда отправить |
| `ReportService::Sender` | Контракт операции: `void(const std::string&)` |
| `ConsoleSender` или записывающая лямбда | Выполняет доставку |

Вызов проходит так:

```text
reports.complete("sales")
  → формирование "Report ready: sales"
  → sender_(message)
  → лямбда вызывает console.send(message)
```

`ReportService` получает обработчик через конструктор. Это также пример
передачи зависимости извне: сервису не нужно самостоятельно создавать
конкретный способ доставки. Пустой обработчик здесь считается ошибкой
конфигурации и отвергается конструктором.

`std::function` — средство хранения вызываемого объекта, а делегирование —
отношение между участниками программы. Одно не требует другого.

## Альтернатива: интерфейс с виртуальным методом

Когда у помощника несколько связанных операций, часто понятнее интерфейс:

```cpp
struct Sender {
    virtual ~Sender() = default;
    virtual void send(const std::string& message) = 0;
};

class ReportService {
public:
    explicit ReportService(Sender& sender) : sender_(sender) {}

    void complete(const std::string& title) {
        sender_.send("Report ready: " + title);
    }

private:
    Sender& sender_; // Не владеет; sender должен жить дольше сервиса.
};
```

Это самостоятельная альтернатива классу из `delegate.cpp`, а не дополнение
с тем же именем в одной программе. Сам подход с виртуальным интерфейсом
доступен в C++98; показанный синтаксис `= default` требует C++11.
Для одной операции обычно достаточно callback; для группы операций
интерфейс даёт связанные имена и явный контракт.

## Отличие от соседних понятий

| Понятие | На какой вопрос отвечает |
|---|---|
| Делегирование | Кому объект поручает часть работы? |
| Callback | Какой обработчик другой код должен вызвать? |
| Strategy | Каким взаимозаменяемым алгоритмом выполнить задачу? |
| Observer | Как уведомить подписчиков об изменении или событии? |
| Decorator | Как добавить поведение, сохранив интерфейс обёрнутого объекта? |

Один пример может сочетать несколько идей. Смена способа доставки у
`ReportService` близка к Strategy. [Механизм Event](../c++11/functional/events.md)
с несколькими подписчиками ближе к Observer: отправитель уведомляет всех
подписчиков, а не выбирает одного исполнителя поручения.
Сравни также существующие примеры [Observer](observer.cpp)
и [Decorator](decorator.md).

## Время жизни и ограничения

В примере лямбда захватывает `console` по ссылке, поэтому он должен
существовать при каждом вызове `complete()`. В `main()` получатель создаётся
раньше сервиса и разрушается позже него. Сервис не владеет получателем.

Вариант со `std::function` добавляет требования к копируемости обработчика,
может выделять память и требует косвенного вызова. Вариант с интерфейсом
требует отдельного типа и виртуального вызова. Выбирай по необходимому
контракту и владению; универсальный класс `Delegate` для этого урока не нужен.

## Запуск и практика

Из корня репозитория:

```bash
cmake -S . -B build
cmake --build build --target cpp11_delegate_example
./build/c++11/functional/cpp11_delegate_example
```

Или напрямую:

```bash
c++ -std=c++11 -Wall -Wextra -Wpedantic patterns/delegate.cpp -o /tmp/delegate_example
/tmp/delegate_example
```

Вывод:

```text
console: Report ready: sales
recorded: Report ready: inventory
```

1. Напиши второго получателя, сохраняющего сообщения в `std::vector<std::string>`.
   Два вызова `complete()` должны сохранить два сообщения в порядке вызовов.
2. Замени callback реализацией через виртуальный интерфейс `Sender`.
3. Объясни, что изменится при захвате получателя по значению вместо ссылки.
4. Назови разницу между обязательным делегатом сервиса и необязательным
   подписчиком события. Какой вариант уместен для доставки отчёта,
   а какой — для уведомления нескольких экранов о готовности?
