# Inode: индексные дескрипторы, жёсткие и символические ссылки

## Что такое айнода и индексный дескриптор

**Inode (айнода, также говорят «айнод» или «инод») — индексный дескриптор**:
структура файловой системы, которая описывает файл или каталог.
Это названия одного понятия. По этой структуре система получает
служебную информацию об объекте и находит его данные.

Представь карточку файла: в ней записаны свойства и сведения о расположении
данных. У карточки есть номер — **номер inode**. Сам номер и структура,
которую он идентифицирует, — связанные, но разные вещи.

| Информация inode | Что означает |
|---|---|
| Тип объекта | Обычный файл, каталог, символическая ссылка и другие типы |
| Права доступа | Разрешения на чтение, запись и выполнение |
| UID и GID | Идентификаторы владельца и группы |
| Размер | Логический размер файла в байтах |
| Число жёстких ссылок | Сколько записей каталогов ссылаются на этот inode |
| Временные метки | Доступ, изменение содержимого и изменение состояния inode |
| Сведения о данных | Информация, по которой файловая система находит содержимое |

`atime` — время последнего доступа, `mtime` — изменения содержимого,
`ctime` — изменения состояния inode, например прав или числа ссылок.
**`ctime` не является временем создания.** Отдельная метка создания
`btime` / birth time доступна не во всех файловых системах и интерфейсах.

Имя и полный путь не хранятся в inode. Содержимое обычного файла обычно
хранится в блоках данных; конкретное размещение зависит от файловой системы.
Например, короткий путь символической ссылки может храниться внутри inode.
Каталоги и символические ссылки тоже имеют свои inode.

Номер inode уникален только в пределах одной файловой системы.
Для сравнения одновременно существующих объектов нужна пара
«устройство + inode». После освобождения inode его номер может
использоваться повторно для другого файла.

## Где хранится имя файла

Каталог содержит записи, связывающие имена с номерами inode.
Упрощённый пример содержимого одного каталога:

| Имя в каталоге | Номер inode |
|---|---|
| `original.txt` | `42001` |
| `hard.txt` | `42001` |
| `soft.txt` | `42002` |

Числа условные. Два первых имени ведут к одной структуре и общим данным.
Третье имя ведёт к отдельному объекту — символической ссылке.
Её содержимое задаёт путь к цели.

При открытии пути система последовательно разрешает его компоненты
через каталоги. Сначала находит имя, затем соответствующий inode
и необходимые данные. Переименование внутри одной файловой системы
меняет связь с именем, сохраняя сам объект.

## Индексный и файловый дескрипторы — разные понятия

| Понятие | Где используется | Пример |
|---|---|---|
| Индексный дескриптор, inode | В файловой системе, описывает объект | Inode номер `42001` |
| Файловый дескриптор, FD | В таблице дескрипторов конкретного процесса | `0`, `1`, `2`, `3` |

При открытии файла процесс получает файловый дескриптор — небольшое
неотрицательное число для последующих операций чтения и записи.
У двух процессов FD `3` может обозначать разные открытые файлы.
Открытие файла не создаёт дополнительную жёсткую ссылку и не увеличивает
её счётчик, но открытый файл может продолжать существовать после удаления имени.
Это проверим отдельно в практике ниже.

## Как устроены ссылки

Hard link — жёсткая ссылка. Symbolic link, symlink и soft link —
разные названия символической ссылки.

У одного обычного файла может быть несколько имён, в том числе в разных
каталогах. Каждое такое имя — жёсткая ссылка на один и тот же inode.
Первое имя файла тоже является жёсткой ссылкой.

```text
original.txt ──┐
              ├── inode A ── данные файла
hard.txt ──────┘

soft.txt ── inode B ── путь "original.txt" ── inode A
```

У символической ссылки свой inode. Она хранит путь, который система
разрешает при обращении к целевому файлу. Символическая ссылка
не увеличивает число жёстких ссылок на целевой inode.

## Сравнение

| Свойство | Hard link | Symbolic / soft link |
|---|---|---|
| На что ссылается | На тот же inode | На путь к цели |
| Свой inode | Нет, общий с файлом | Да |
| Копирует содержимое файла | Нет | Нет |
| Работает между разными файловыми системами | Нет | Да, если цель доступна |
| Можно создать на каталог | В обычной работе Linux нельзя | Да |
| Можно создать до появления цели | Нет | Да |
| После удаления другого имени файла | Данные доступны через оставшееся имя | Становится битой, если её путь больше не существует |
| После замены файла новым по тому же пути | Остаётся связанной со старым inode | Разрешается в новый файл |

Жёсткие ссылки равноправны: у них нет выделенного «оригинала».
Слово `original` ниже — только удобное имя для первого файла.

## Подготовка

Примеры предназначены для Bash в Linux и используют возможности
GNU-совместимых `ln`, `stat`, `find` и `readlink`.
Выполняй блоки по порядку в одной оболочке:

```bash
work_dir=$(mktemp -d /tmp/linux-links.XXXXXX)
printf 'Учебный каталог: %s\n' "$work_dir"
printf 'First version\n' > "$work_dir/original.txt"
```

`mktemp -d` создаёт новый каталог, а `$(...)` сохраняет его путь
в переменную. Кавычки вокруг путей сохраняют их одним аргументом.
`--` завершает список опций команды.

## Сначала смотрим inode одного файла

```bash
ls -lid -- "$work_dir" "$work_dir/original.txt"
stat -- "$work_dir/original.txt"
stat -c '%n: device=%d inode=%i links=%h size=%s mode=%a uid=%u gid=%g' -- \
    "$work_dir/original.txt"
df -i -- "$work_dir"
```

У каталога и обычного файла разные inode. Опция `-d` у `ls` показывает
сам каталог, а не его содержимое. У только что созданного обычного файла
счётчик жёстких ссылок равен `1`: первое имя тоже считается ссылкой.

В полном выводе `stat` найди `Inode`, `Links`, `Size`, `Access`, `Modify`,
`Change` и, если доступно, `Birth`. `Access` встречается и для прав доступа,
и для времени доступа: смотри на значение рядом с подписью.

`df -i` показывает использование inode файловой системой, содержащей путь.
Ограничения и способ учёта зависят от файловой системы. В частности,
на ext4 свободные байты не гарантируют наличие свободных inode:
множество мелких файлов может исчерпать их раньше места под данные.

## Создание: ln и ln -s

Общий синтаксис: `ln цель новое_имя`.
Без `-s` создаётся жёсткая ссылка, с `-s` — символическая:

```bash
ln -- "$work_dir/original.txt" "$work_dir/hard.txt"
ln -s -- original.txt "$work_dir/soft.txt"
```

Вторая команда записывает в ссылку относительный путь `original.txt`.
Он отсчитывается от каталога, содержащего `soft.txt`, а не от текущего
каталога оболочки. Поэтому обе команды работают из корня проекта.

По умолчанию новое имя не должно существовать. `ln` завершится с ошибкой,
если файл с таким именем уже есть. Если последний аргумент — существующий
каталог, `ln` создаёт ссылку внутри него с именем цели.

## Как увидеть разницу: ls, stat и readlink

```bash
ls -li -- "$work_dir/original.txt" "$work_dir/hard.txt" "$work_dir/soft.txt"
stat -c '%n: device=%d inode=%i links=%h type=%F' -- \
    "$work_dir/original.txt" "$work_dir/hard.txt" "$work_dir/soft.txt"
readlink -- "$work_dir/soft.txt"
readlink -e -- "$work_dir/soft.txt"
```

На что обратить внимание:

- В `ls -li` первый столбец — номер inode. У `original.txt` и `hard.txt`
  он одинаковый, а число жёстких ссылок в длинном выводе равно `2`.
- У `soft.txt` отдельный inode, тип в начале строки — `l`,
  а после имени показана стрелка `-> original.txt`.
- `stat` по умолчанию описывает саму символическую ссылку.
  `stat -L` следует по ссылке и описывает цель.
- `readlink` выводит записанный путь: `original.txt`.
  `readlink -e` выводит полный разрешённый путь, только если все его
  компоненты существуют. Иначе команда завершается с ненулевым кодом.

В формате `stat`: `%d` — номер устройства, `%i` — inode,
`%h` — число жёстких ссылок, `%F` — тип файла, `%n` — имя.
Номер inode уникален только внутри файловой системы: для сравнения
нужна пара «устройство + inode». Конкретные числа при каждом запуске разные.

## Несколько имён и счётчик жёстких ссылок

```bash
ln -- "$work_dir/hard.txt" "$work_dir/another-hard.txt"
stat -c '%n: inode=%i links=%h' -- \
    "$work_dir/original.txt" "$work_dir/hard.txt" "$work_dir/another-hard.txt"
```

Теперь три имени ведут к одному inode, поэтому для каждого `links=3`.
Счётчик относится к общему объекту, а не к отдельному имени.
Создавать новое имя можно через уже существующую жёсткую ссылку.

Найдём имена внутри учебного дерева двумя способами:

```bash
inode_number=$(stat -c '%i' -- "$work_dir/original.txt")
find "$work_dir" -xdev -inum "$inode_number" -print
find "$work_dir" -xdev -samefile "$work_dir/original.txt" -print
```

`-inum` сравнивает только номер inode, `-samefile` — идентичность объекта
по устройству и inode. `-xdev` запрещает спуск в другие файловые системы.
Поиск ограничен указанным деревом: имена вне него не будут показаны.
По умолчанию `find` не следует по символическим ссылкам, поэтому
`soft.txt` в этот результат не попадёт.

Удалим добавленное имя и посмотрим на оставшиеся:

```bash
rm -- "$work_dir/another-hard.txt"
stat -c '%n: inode=%i links=%h' -- "$work_dir/original.txt" "$work_dir/hard.txt"
```

Счётчик стал `2`. Содержимое не копировалось ни при создании,
ни при удалении дополнительного имени. Расходы на запись в каталоге
остаются, поэтому «не копирует данные» не означает «вообще не занимает места».

## Изменение содержимого и отличие от копии

```bash
printf 'Added through hard link\n' >> "$work_dir/hard.txt"
printf 'Added through soft link\n' >> "$work_dir/soft.txt"
cat -- "$work_dir/original.txt" "$work_dir/soft.txt"
cp -- "$work_dir/original.txt" "$work_dir/copy.txt"
printf 'Only in copy\n' >> "$work_dir/copy.txt"
```

Изменение через `hard.txt` видно через оба других имени.
Запись через `soft.txt` следует по пути и меняет целевой файл,
а не строку пути, хранящуюся в самой ссылке.
`cp` создаёт отдельный файл: изменение `copy.txt` не меняет исходный файл.
Жёсткая ссылка не является резервной копией: содержимое и права доступа
у неё общие с остальными именами того же inode.

Это можно проверить и для прав:

```bash
chmod 600 -- "$work_dir/hard.txt"
stat -c '%n: mode=%a uid=%u gid=%g' -- "$work_dir/original.txt" "$work_dir/hard.txt"
```

У обоих имён права станут `600`, поскольку изменён общий inode.
Сама символическая ссылка не обходит права целевого файла.

## Переименование и битая ссылка

```bash
mv -- "$work_dir/original.txt" "$work_dir/renamed.txt"
cat -- "$work_dir/hard.txt"
readlink -- "$work_dir/soft.txt"
if [[ -L "$work_dir/soft.txt" && ! -e "$work_dir/soft.txt" ]]; then
    printf 'Ссылка есть, но её цель отсутствует\n'
fi
```

Переименование в пределах одной файловой системы сохраняет inode.
`hard.txt` продолжает работать, а `soft.txt` всё ещё хранит старый путь
`original.txt` и становится битой (dangling / broken symlink).

Проверка `-L` проверяет саму символическую ссылку, а `-e` следует по ней.
Для битой ссылки `-L` истинно, `-e` ложно. Здесь цель заведомо удалена
из пути; в общем случае ошибка доступа тоже может помешать проверке `-e`.

Вернём имя, и та же символическая ссылка снова заработает:

```bash
mv -- "$work_dir/renamed.txt" "$work_dir/original.txt"
cat -- "$work_dir/soft.txt"
```

Перемещение между файловыми системами может выполняться через копирование
и удаление: сохранение inode при этом не гарантируется.

## Изменить файл и заменить файл — разные операции

Некоторые редакторы сохраняют данные в новый файл и переименовывают его
поверх старого. Смоделируем такую замену:

```bash
printf 'Replacement version\n' > "$work_dir/replacement.txt"
mv -f -- "$work_dir/replacement.txt" "$work_dir/original.txt"
cat -- "$work_dir/hard.txt"
cat -- "$work_dir/soft.txt"
stat -c '%n: inode=%i links=%h' -- "$work_dir/original.txt" "$work_dir/hard.txt"
```

Теперь `original.txt` указывает на новый inode. Символическая ссылка
находит новый файл по прежнему пути. `hard.txt` продолжает показывать
старое содержимое, потому что связана со старым inode.

Это отличается от `printf 'text\n' > существующий_файл`: обычное
перенаправление очищает существующий файл и записывает данные в тот же
inode, поэтому изменение видно через все его жёсткие ссылки.

## Удаление имён

```bash
rm -- "$work_dir/original.txt"
cat -- "$work_dir/hard.txt"
rm -- "$work_dir/soft.txt"
rm -- "$work_dir/hard.txt"
```

Удаление имени уменьшает число жёстких ссылок на соответствующий inode.
Данные обычного файла могут быть освобождены, когда удалена последняя
жёсткая ссылка и нет открытых дескрипторов или других ссылок ядра,
которые удерживают файл, например отображений в память.

Удаление символической ссылки удаляет саму ссылку, а не её цель.
После последней команды старые данные всё ещё есть в независимом `copy.txt`.

## Открытый файл после удаления последнего имени

Проверим отличие inode от файлового дескриптора:

```bash
printf 'Still available through FD 3\n' > "$work_dir/opened.txt"
exec 3< "$work_dir/opened.txt"
rm -- "$work_dir/opened.txt"
stat -L -c 'Открытый файл: inode=%i links=%h' -- "/proc/$$/fd/3"
cat <&3
exec 3<&-
```

`exec 3<` открывает файл для чтения через FD `3` в текущем Bash.
Здесь `exec` без команды меняет перенаправления самой оболочки.
`/proc/$$/fd/3` в Linux позволяет обратиться к её открытому дескриптору.
`stat -L` следует по этому пути и показывает `links=0`: имён уже нет,
но данные ещё доступны через открытый файл.

`cat <&3` читает через дескриптор, а `exec 3<&-` закрывает его.
Если больше никто не удерживает объект, файловая система может освободить
его ресурсы. Это также объясняет, почему удалённый лог иногда продолжает
занимать место до закрытия его программой.

## Относительные и абсолютные символические ссылки

```bash
mkdir -p "$work_dir/package/data" "$work_dir/package/links"
printf 'Portable data\n' > "$work_dir/package/data/message.txt"
ln -s -- ../data/message.txt "$work_dir/package/links/message"
ln -s -- "$work_dir/package/data/message.txt" "$work_dir/package/links/absolute-message"
cat -- "$work_dir/package/links/message"
mv -- "$work_dir/package" "$work_dir/moved-package"
cat -- "$work_dir/moved-package/links/message"
readlink -- "$work_dir/moved-package/links/absolute-message"
if [[ -L "$work_dir/moved-package/links/absolute-message" && \
      ! -e "$work_dir/moved-package/links/absolute-message" ]]; then
    printf 'Абсолютная ссылка хранит прежний путь и стала битой\n'
fi
```

Путь `../data/message.txt` отсчитывается от каталога `links`.
При переносе всего дерева относительная связь сохранилась.
Если переместить только саму ссылку в другой каталог, тот же путь
будет разрешаться уже от нового расположения и может перестать работать.

Абсолютный путь начинается с `/` и привязывает ссылку к конкретному месту.
В примере `absolute-message` хранит старый абсолютный путь:
после переименования каталога `package` такого пути уже нет.
Оба вида путей допустимы; выбор зависит от того, что будет перемещаться.
Цель не обязана существовать в момент создания символической ссылки.

Ссылка также может вести в другую файловую систему по доступному пути,
например в смонтированную сетевую папку. Обычная символическая ссылка
сама по себе не подключается к удалённому компьютеру и не скачивает файл.

## Ссылки на каталоги

```bash
mkdir "$work_dir/real-directory"
printf 'Keep me\n' > "$work_dir/real-directory/keep.txt"
ln -s -- real-directory "$work_dir/directory-link"
cat -- "$work_dir/directory-link/keep.txt"
rm -- "$work_dir/directory-link"
cat -- "$work_dir/real-directory/keep.txt"
```

Удаляем имя ссылки без завершающего `/`: настоящий каталог остаётся.
Жёсткие ссылки на каталоги обычной командой `ln` в Linux не создаются,
чтобы не нарушать структуру дерева каталогов.

Проверим обратную ситуацию — удаление самой цели:

```bash
ln -s -- real-directory "$work_dir/directory-link"
rm -r -- "$work_dir/real-directory"
ls -ld -- "$work_dir/directory-link"
if [[ -L "$work_dir/directory-link" && ! -e "$work_dir/directory-link" ]]; then
    printf 'Ссылка на удалённый каталог стала битой\n'
fi
```

Имя ссылки осталось. Чтение `directory-link/keep.txt` теперь завершится
ошибкой отсутствия пути; это отличается от чтения существующего пустого каталога.

## Поиск символических ссылок

```bash
find "$work_dir" -type l -print
```

По умолчанию `find` не следует по обнаруженным символическим ссылкам
и с `-type l` выводит сами ссылки, включая битые.

## Практика

1. Создай новый временный каталог и обычный файл. Через `stat` найди номер
   inode, размер, владельца, права и число ссылок. Где хранится имя файла?
2. Создай две жёсткие ссылки и одну символическую. Предскажи значения inode
   и числа ссылок. Найди все жёсткие имена через `find -samefile` в этом каталоге.
3. Добавь строки через жёсткую и символическую ссылки. Измени права через
   жёсткую ссылку. Проверь содержимое и метаданные через остальные имена.
4. Удали первое имя файла. Проверь оставшиеся жёсткие ссылки и символическую.
   Почему `ls` видит битую ссылку, а `cat` не читает её цель?
5. Восстанови файл по старому пути с другим содержимым.
   Сравни его со старой жёсткой ссылкой и целью символической ссылки.
6. Создай относительную и абсолютную ссылки на файл в соседнем каталоге.
   Перенеси всё дерево, затем только относительную ссылку: объясни разницу.
7. Создай символическую ссылку на ещё не существующий файл.
   Затем создай цель и проверь ссылку через `readlink`, `readlink -e` и `cat`.
8. Открой отдельный файл через FD `3`, удали его имя и посмотри число ссылок
   через `/proc/$$/fd/3`. Прочитай данные и закрой дескриптор.
   Почему открытие не увеличило число жёстких ссылок?

После ручных примеров проверь путь и удали учебный каталог:

```bash
printf '%s\n' "$work_dir"
rm -r -- "$work_dir"
unset work_dir inode_number
```

## Запуск примеров

Из корня проекта:

```bash
bash linux/links/examples.sh
```

Скрипт создаёт свои данные в новом временном каталоге и удаляет его
при выходе. Можно запускать повторно; файлы проекта не меняются.
Для повторения удаления смотри [модуль rm и rmdir](../../bash/rm/notes.md).

## Статья и уточнения

Материал дополнен по статье Timeweb Cloud
[«О мягких и жёстких ссылках в Linux»](https://habr.com/ru/companies/timeweb/articles/925150/):
использован порядок наблюдений за созданием, редактированием и удалением ссылок.
Объяснение написано самостоятельно, примеры адаптированы к временному каталогу.

В статье есть неточные формулировки. Жёсткая ссылка — дополнительное имя
общего объекта, а не зеркальная копия. Относительные пути в символических
ссылках работают и отсчитываются от каталога ссылки. Доступ к удалённому файлу
требует доступного локального пути, например через сетевое монтирование.
Эти уточнения проверяются примерами и системной документацией.

- [symlink(7)](https://man7.org/linux/man-pages/man7/symlink.7.html) — символические ссылки и их обработка.
- [open(2)](https://man7.org/linux/man-pages/man2/open.2.html) — файловые дескрипторы.
- [unlink(2)](https://man7.org/linux/man-pages/man2/unlink.2.html) — удаление имени открытого файла.
