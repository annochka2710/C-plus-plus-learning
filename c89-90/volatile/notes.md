# Ключевое слово volatile в C89/C90

`volatile` — квалификатор типа. Он указывает, что обращения к объекту
значимы сами по себе: значение может меняться способом, который компилятор
не видит из обычного потока выполнения, а запись может воздействовать
на внешнее устройство.

Объяснение цикла ниже адаптировано по идее ответа Sarfaraz Nawaz
в [Why do we use the volatile keyword?](https://stackoverflow.com/questions/4437527/why-do-we-use-the-volatile-keyword).
Исходный вопрос относится к C++; здесь рассматриваем C89/C90,
а запускаемые примеры написаны специально для этого модуля.

## Идея на примере цикла

```c
int some_int = 100;

while (some_int == 100) {
    /* Внутри нет действий, которые меняют some_int. */
}
```

Если компилятор установит, что значение не меняется, он может убрать
повторные чтения и сравнения. Для этой локальной переменной условие
всегда истинно, поэтому программа останется в цикле.

Квалификатор меняет требования к обращениям:

```c
volatile int some_int = 100;
```

Теперь при каждой проверке условия требуется новое обращение к объекту.
Но `volatile` не создаёт источник изменений: без устройства или корректно
организованного обработчика значение по-прежнему останется `100`.
Этот фрагмент объясняет идею, а практический выход из цикла показан
в [signal_example.c](signal_example.c).

## Что именно меняется для оптимизатора

Сравни функции в [examples.c](examples.c):

```c
first = *value;
second = *value;
```

При обычном указателе компилятор может прочитать значение один раз
и использовать его дважды. Для указателя на `volatile`-объект эти
отдельные полные выражения требуют двух чтений.

Аналогично для записей:

```c
*value = 1U;
*value = 2U;
```

У обычного объекта первую запись можно убрать, поскольку её результат
перезаписывается. При обращении через `volatile` обе записи значимы.
Например, для аппаратного регистра последовательность команд `1`, затем `2`
может отличаться от единственной команды `2`.

`volatile` не отключает оптимизацию функции или программы целиком.
Точные правила аппаратного доступа зависят от реализации; в частности,
GCC описывает их в [документации об обращениях к volatile](https://gcc.gnu.org/onlinedocs/gcc/Volatiles.html).

## Где применяется

- Регистры устройств, отображённые в адресное пространство памяти (MMIO).
  Адрес, ширина доступа и дополнительные барьеры определяются платформой.
- Простой флаг между обработчиком сигнала и основным кодом:
  `volatile sig_atomic_t` из `<signal.h>`.

Произвольный адрес не становится доступным после добавления `volatile`.
В примерах модуля нет обращения к реальным аппаратным регистрам.

## Чего volatile не гарантирует

| Свойство | Гарантия |
|---|---|
| Сохранение значимых volatile-обращений | Да, по правилам реализации C |
| Атомарность `int`, `long` или `counter++` | Нет |
| Синхронизация потоков | Нет |
| Упорядочивание всех обращений к обычной памяти | Нет |
| Отключение кеша процессора | Нет |
| Постоянное изменение значения | Нет |

В C89/C90 нет стандартных потоков и атомиков. В более позднем C
для обмена между потоками используют атомики C11 или подходящие средства
синхронизации, например мьютексы. Одного `volatile` для этого недостаточно.
В частности, [GCC не рассматривает volatile как барьер для обычной памяти](https://gcc.gnu.org/onlinedocs/gcc/Volatiles.html).

## Практический флаг: volatile sig_atomic_t

Основные части [signal_example.c](signal_example.c):

```c
static volatile sig_atomic_t stop_requested = 0;

static void handle_interrupt(int signal_number)
{
    (void)signal_number;
    stop_requested = 1;
}
```

В `main` обработчик устанавливается через `signal(SIGINT, handle_interrupt)`.
Затем цикл читает флаг:

```c
while (!stop_requested) {
    /* Ждём изменения флага. */
}
```

В терминале Linux `Ctrl+C` обычно отправляет `SIGINT` группе процессов
переднего плана. Обработчик присваивает флагу `1`, возвращается,
и основной код завершает цикл.

Здесь две отдельные задачи: `volatile` сохраняет чтения флага,
а тип `sig_atomic_t` позволяет безопасное простое присваивание в контексте
обработчика сигнала. Из этого не следует атомарность `++` или пригодность
такого флага для обмена между потоками.

Обработчик не печатает сообщения: он только выставляет флаг. Вывод
выполняется после цикла в `main`. Ограничения обработчиков разобраны
в [руководстве GNU C Library](https://ftp.gnu.org/old-gnu/Manuals/glibc-2.2.3/html_chapter/libc_24.html).

Цикл использует активное ожидание и занимает процессор. Здесь это сделано,
чтобы наблюдать повторное чтение. В прикладной программе способ ожидания
событий выбирают отдельно. Нажимай `Ctrl+C` один раз: поведение установки
обработчика после сигнала зависит от реализации `signal`.

## Volatile-данные и volatile-указатель

| Объявление | Что квалифицировано |
|---|---|
| `volatile int *p` | Объект, доступный через `*p` |
| `int * volatile p` | Сам указатель `p` |
| `volatile int * volatile p` | Указатель и объект через него |
| `const volatile int *p` | Объект читается через volatile-доступ; записывать через `*p` нельзя |

`const volatile` не противоречие: программный доступ через этот указатель
не разрешает запись, но значение может меняться извне, как у регистра
состояния устройства.

## Сборка и запуск

Из корня проекта, отдельно от C++-примеров:

```bash
mkdir -p build
cc -std=c90 -pedantic-errors -Wall -Wextra -Wstrict-prototypes -O2 \
    c89-90/volatile/examples.c -o build/volatile_examples
./build/volatile_examples
```

Ожидаемый вывод:

```text
Обычное чтение: 20
Чтение volatile: 20
После обычных записей: 2
После volatile-записей: 2
```

Одинаковый результат ожидаем: никто не меняет значения извне.
Разница видна в обращениях, которые оставляет компилятор.

```bash
cc -std=c90 -pedantic-errors -Wall -Wextra -Wstrict-prototypes -O2 \
    c89-90/volatile/signal_example.c -o build/volatile_signal
./build/volatile_signal
```

После первого сообщения нажми `Ctrl+C` один раз. Программа должна вывести:

```text
Флаг получен. Программа завершилась через main.
```

В обоих файлах используются комментарии `/* ... */`, объявления
до операторов в блоке и функции с прототипами: код соответствует C89/C90.
В GCC имена режимов `-std=c89` и `-std=c90` обозначают одну версию языка.

## Посмотреть ассемблер

```bash
cc -std=c90 -pedantic-errors -O2 -S \
    c89-90/volatile/examples.c -o build/volatile_examples.s
less build/volatile_examples.s
```

Найди `read_twice` и `read_twice_volatile`, затем `write_twice`
и `write_twice_volatile`. На типичной сборке GCC с `-O2` первая пара
показывает одно чтение против двух, вторая — одну запись против двух.
Инструкции зависят от архитектуры и компилятора; при `-O0` разница
может быть менее заметной.

## Практика

1. Собери `examples.c` с `-O0` и `-O2`. Сравни вывод и ассемблер четырёх функций.
2. Объясни, почему одинаковый вывод не доказывает бесполезность `volatile`.
3. Запусти пример с сигналом. Почему обработчик только присваивает `1`,
   а сообщение печатает `main`?
4. Объясни отдельно назначение `volatile` и `sig_atomic_t`.
5. Нарисуй типы для `volatile int *p` и `int * volatile p`.
   Через какой указатель выполняется volatile-чтение объекта `int`?
6. Объясни, почему `volatile unsigned int counter; counter++;`
   не решает задачу счётчика, который одновременно меняют два потока.

Не удаляй квалификатор из рабочего примера с асинхронным сигналом,
рассчитывая получить корректное сравнение: такой вариант нарушает
правила доступа из обработчика. Для сравнения оптимизаций используй
обычные и volatile-функции из `examples.c`.
