# std::jthread, std::this_thread и std::ref

Эти средства часто встречаются вместе: запускаем работу в потоке,
передаём ему данные и затем ожидаем завершения.

| Средство | Стандарт | Заголовок | Назначение |
|---|---|---|---|
| `std::thread` | C++11 | `<thread>` | Объект, управляющий потоком выполнения |
| `std::this_thread` | C++11 | `<thread>` | Пространство имён с функциями для текущего потока |
| `std::ref`, `std::cref` | C++11 | `<functional>` | Копируемые обёртки над ссылками |
| `std::jthread` | C++20 | `<thread>` | Поток с автоматическим ожиданием завершения и поддержкой запроса остановки |
| `std::stop_token` | C++20 | `<stop_token>` | Проверка запроса остановки |

Материал связан с [лямбдами](../../c++11/functional/lambdas.md)
и [std::bind](../../c++11/functional/notes.md).

## std::ref: сохранить обращение к исходному объекту

Обычная ссылка `T&` — часть системы типов. `std::ref(value)` возвращает
объект `std::reference_wrapper<T>`, который можно копировать,
сохраняя обращение к тому же `value`. Через `.get()` получаем `T&`.

```cpp
#include <functional>

int value = 10;
auto reference = std::ref(value);
auto another = reference;
another.get() += 5; // value == 15.
```

`std::cref(value)` создаёт `std::reference_wrapper<const T>`: менять
объект через эту обёртку нельзя. Сам объект при этом не становится
константным для всех остальных обращений. Эти обёртки не владеют объектом
и не продлевают его жизнь. `std::ref(42)` и `std::cref(42)` запрещены.
См. [reference_wrapper](https://eel.is/c++draft/refwrap)
и [ref/cref](https://eel.is/c++draft/refwrap.helpers).

### Зачем ref при запуске потока

При обычной передаче аргументов `std::thread` сохраняет их собственные
значения: lvalue копируются, rvalue могут перемещаться. Это относится
и к `std::jthread`. Для обращения к исходному объекту передай обёртку:

```cpp
void increment(int& value) { ++value; }

int value = 10;
std::thread worker(increment, std::ref(value));
worker.join();
// value == 11; читать его теперь безопасно.
```

`std::thread worker(increment, value);` не скомпилируется: сохранённый
аргумент не может связаться с требуемой неконстантной lvalue-ссылкой.
Если функция принимает `int` по значению, она меняет свою локальную копию,
даже при передаче `std::ref(value)`.
См. [конструктор thread](https://eel.is/c++draft/thread.thread.constr)
и [конструктор jthread](https://eel.is/c++draft/thread.jthread.cons).

Для прямого синхронного вызова достаточно `increment(value)`.
Для лямбды можно захватить ссылку: `std::thread worker([&value] { ++value; });`.
Требования к времени жизни и синхронизации остаются теми же.

В [ref_examples.cpp](ref_examples.cpp) сравниваются копия, обёртка,
изменение оригинала из потока и чтение через `std::cref`.

## std::this_thread: действия текущего потока

Это пространство имён, а не класс и не объект потока.

| Вызов | Что делает |
|---|---|
| `std::this_thread::get_id()` | Возвращает идентификатор вызывающего потока |
| `std::this_thread::sleep_for(duration)` | Приостанавливает вызывающий поток на заданный интервал |
| `std::this_thread::sleep_until(time_point)` | Приостанавливает вызывающий поток до заданного момента |
| `std::this_thread::yield()` | Даёт планировщику возможность переключить выполнение |

```cpp
std::this_thread::sleep_for(std::chrono::milliseconds(10)); // C++11.

using namespace std::chrono_literals;
std::this_thread::sleep_for(10ms); // Суффикс ms доступен с C++14.
```

Сон может закончиться позже из-за планирования и нагрузки.
Для измерения интервалов удобно использовать `std::chrono::steady_clock`.
`yield()` не гарантирует, что обязательно запустится другой поток.
Сон и `yield()` не синхронизируют доступ к данным.
См. [this_thread](https://eel.is/c++draft/thread.thread.this)
и [требования к тайм-аутам](https://eel.is/c++draft/thread.req.timing).

`worker.get_id()` запрашивает идентификатор потока, связанного с объектом
`worker`. `std::this_thread::get_id()` возвращает идентификатор того потока,
который прямо сейчас выполняет вызов. Например, вызов из `main()` относится
к главному потоку, а из рабочей лямбды — к рабочему.

В [this_thread_examples.cpp](this_thread_examples.cpp) показаны оба
идентификатора, относительное ожидание, ожидание до момента и `yield()`.
Идентификаторы и измеренное время зависят от запуска.

## std::jthread: автоматическое ожидание завершения

Объект запускает поток при конструировании с функцией. Сам `jthread`
можно перемещать, но нельзя копировать.

```cpp
int result = 0;
{
    std::jthread worker([&result] { result = 42; });
} // Деструктор запрашивает остановку и ожидает завершения.
// result == 42.
```

Если `jthread` остаётся `joinable()`, его деструктор вызывает
`request_stop()`, затем `join()`. У функции без `stop_token` запрос
не прерывает вычисление: деструктор ожидает её обычного завершения.
См. [jthread и его деструктор](https://eel.is/c++draft/thread.jthread.cons).

| Ситуация | `std::thread` | `std::jthread` |
|---|---|---|
| Объект уничтожается, оставаясь `joinable()` | Вызывает `std::terminate()` | Запрашивает остановку и выполняет `join()` |
| Явный `join()` | Ожидает завершения | Ожидает завершения |
| Встроенный запрос остановки | Нет | `request_stop()` и `stop_token` |

`joinable()` означает, что объект связан с потоком, который ещё не был
присоединён или отделён. Даже уже закончившийся поток остаётся `joinable()`
до `join()` или `detach()`. Проверка не сообщает, выполняется ли функция сейчас.
См. [операции jthread](https://eel.is/c++draft/thread.jthread.mem)
и [деструктор thread](https://eel.is/c++draft/thread.thread.destr).

### Получение результата через join

```cpp
int result = 0;
std::jthread worker([&result] { result = 42; });
worker.join();
std::cout << result << '\n';
```

Успешный `join()` синхронизирует завершение рабочего потока с продолжением
вызывающего. В примере запись завершена до чтения, поэтому для `result`
не требуется `atomic`. Если читать или менять его одновременно с рабочим
потоком, нужна отдельная синхронизация: например, мьютекс или подходящая
атомарная операция. `std::ref` сам по себе синхронизации не добавляет.
См. [гарантии join](https://eel.is/c++draft/thread.jthread.mem).

## stop_token: остановка по запросу

```cpp
std::jthread worker([](std::stop_token token) {
    while (!token.stop_requested()) {
        // Небольшая порция работы.
        std::this_thread::sleep_for(std::chrono::milliseconds(1));
    }
});

worker.request_stop();
worker.join();
```

Когда функция допускает вызов с `std::stop_token` первым аргументом,
`jthread` передаёт свой токен автоматически; далее идут явно переданные
аргументы. Возможен и обычный вызов без токена. В
[examples.cpp](examples.cpp) есть оба варианта.
См. [правила запуска jthread](https://eel.is/c++draft/thread.jthread.cons).

Запрос остановки кооперативный: рабочий код сам проверяет
`token.stop_requested()` и выходит. `request_stop()` не ждёт завершения;
`join()` ждёт, но сам запрос не отправляет. Для цикла, завершаемого только
по токену, сначала вызови `request_stop()`, затем `join()`.

`request_stop()` возвращает `true`, если этот вызов впервые установил
запрос в связанном состоянии остановки. Это не подтверждение завершения
потока. Поток может получить запрос ещё до входа в рабочую функцию.
Не нужно ожидать, что цикл обязательно выполнится хотя бы один раз.
См. [механизм остановки](https://eel.is/c++draft/thread.stoptoken).

`sleep_for()` не прерывается токеном: проверка произойдёт после сна.
Блокирующий ввод-вывод тоже не отменяется автоматически. Поэтому долгий
вызов или игнорирование токена могут надолго задержать деструктор.
Для прерываемого ожидания существует перегрузка `condition_variable_any::wait`
со `stop_token` в C++20; её стоит разбирать вместе с условными переменными.
См. [ожидание с токеном](https://eel.is/c++draft/thread.condvarany.intwait).

## Время жизни и исключения

Объекты, переданные через `std::ref`, `std::cref` или захват по ссылке,
должны жить до последнего обращения рабочего потока. Объявляй данные
раньше объекта `jthread` либо используй вложенный блок: локальные объекты
уничтожаются в обратном порядке. Все примеры читают результаты после
`join()` или после выхода из блока с `jthread`.

Не вызывай `join()` при удержании мьютекса, который нужен рабочему потоку
для завершения. Автоматическое ожидание в деструкторе также может привести
к взаимной блокировке при таком порядке владения ресурсами.

Исключение, вышедшее из функции потока, приводит к `std::terminate()`;
`join()` не переносит его в главный поток. При необходимости перехватывай
исключения внутри рабочей функции и передавай результат через
`std::exception_ptr`, `std::promise`/`std::future` или другой согласованный канал.
См. [вызов функции потока](https://eel.is/c++draft/thread.jthread.cons).

## Сборка и запуск

Из корня проекта:

```bash
cmake -S . -B build
cmake --build build --target cpp11_ref_examples cpp11_this_thread_examples cpp20_jthread_examples
./build/c++20/threads/cpp11_ref_examples
./build/c++20/threads/cpp11_this_thread_examples
./build/c++20/threads/cpp20_jthread_examples
```

Первые два примера собираются в C++11, третий — в C++20.
Для прямой сборки в Linux нужен флаг `-pthread`:

```bash
c++ -std=c++20 -pthread -pedantic-errors -Wall -Wextra -Wshadow -Wconversion \
    c++20/threads/examples.cpp -o /tmp/jthread_examples
/tmp/jthread_examples
```

В примере `ref` исходное число последовательно получает значения 10, 15,
16; результат чтения через `cref` равен 32. В примере `jthread` сумма равна
10, явный и автоматический запросы остановки замечены рабочими потоками.
Число итераций до остановки не фиксируется: оно зависит от планировщика.

## Практика

1. Убери `std::ref` из запуска `increment` и объясни ошибку компиляции.
2. Замени параметр `int&` на `int`. Почему исходное число больше не меняется,
   даже если при запуске осталось `std::ref(value)`?
3. Объясни, почему чтение результата после `join()` безопасно,
   а замена `join()` на `sleep_for(100ms)` этого не гарантирует.
4. Сравни идентификаторы в главном и рабочем потоках. Почему нельзя ожидать
   одних и тех же численных значений при повторном запуске?
5. В демонстрации с вложенным блоком нет явного `request_stop()`.
   Объясни, кто отправляет запрос и почему результат можно читать после блока.
   Затем добавь явный запрос перед выходом из блока и сравни поведение.
6. Объясни, почему `join()` без запроса остановки не завершит бесконечный
   цикл, который выходит только по токену. Такой эксперимент запускай
   с внешним тайм-аутом, затем восстанови `request_stop()`.
7. Добавь конечную задачу с `std::cref` большого вектора и `std::ref`
   результата. Объясни время жизни данных и место безопасного чтения.
