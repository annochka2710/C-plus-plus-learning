# Небольшой механизм событий: подписка и отписка

Предварительные темы: [лямбды](lambdas.md), [std::function](notes.md),
`std::shared_ptr`, `std::map` и `std::vector`.
Весь код использует C++11; это учебный класс, а не встроенная возможность языка.

В [первом примере Button](examples.cpp) был один сменяемый обработчик.
Теперь событие хранит несколько независимых подписок и вызывает их по порядку.
Реализация находится в [event.hpp](event.hpp), демонстрация —
в [event_examples.cpp](event_examples.cpp).

## Интерфейс

```cpp
Event changed;
const auto id = changed.subscribe([](int value) {
    std::cout << value << '\n';
});
changed.emit(42);
changed.unsubscribe(id);
changed.emit(100); // Этот обработчик уже не вызывается.
```

Каждый `subscribe()` создаёт отдельную подписку с собственным идентификатором,
даже если передан тот же обработчик. Сохраняй идентификатор вместе с событием,
которое его выдало: идентификаторы разных событий могут совпадать.
`unsubscribe()` возвращает `true`, если подписка была удалена, иначе `false`.
Передача пустого обработчика бросает `std::invalid_argument`.

Подписка на метод объекта:

```cpp
Counter counter;
Event changed;
const auto id = changed.subscribe([&counter](int value) {
    counter.add(value);
});
changed.emit(5);
changed.unsubscribe(id); // Пока counter ещё существует.
```

Событие хранит копию лямбды. Эта копия содержит ссылку на `counter`,
поэтому событие не владеет получателем и не продлевает его жизнь.
`shared_ptr` внутри реализации владеет записью подписки, а не `counter`.

## Что делает реализация

`std::map<SubscriptionId, std::shared_ptr<Slot>>` хранит записи по идентификаторам.
Каждая запись содержит обработчик и признак `active`.
Идентификаторы растут и не переиспользуются; перед переполнением выдаётся
`std::overflow_error`.

При `emit()` создаётся снимок указателей на текущие записи. Поэтому изменение
таблицы подписок из обработчика не ломает обход. Перед вызовом каждой записи
проверяется `active`. При отписке запись помечается неактивной и удаляется
из таблицы; снимок удерживает её в памяти до завершения текущей рассылки.
Это позволяет обработчику безопасно отписать самого себя.

Почему не скопировать сразу весь список `std::function`? Тогда `mutable`-лямбды
выполнялись бы на временных копиях: изменения их внутреннего состояния
терялись бы после рассылки. Здесь вызывается сохранённый обработчик.

## Правила поведения

| Ситуация | Результат |
|---|---|
| Нет подписчиков | `emit()` ничего не делает |
| Несколько подписчиков | Вызов в порядке подписки |
| Подписка во время рассылки | В текущий снимок не попадает; доступна следующему `emit()` |
| Отписка ещё не вызванного подписчика | Он пропускается уже в текущей рассылке |
| Обработчик отписывает себя | Текущий вызов завершается; следующих вызовов не будет |
| Повторная отписка или неизвестный ID | Возвращается `false` |
| Обработчик бросает исключение | Оно выходит из `emit()`; оставшиеся обработчики не вызываются |
| Вложенный `emit()` | Создаёт свой снимок актуальных подписок и выполняется сразу |

Если из обработчика подписаться и сразу вызвать вложенный `emit()`,
новая подписка получит вложенное событие. Следи за условием завершения,
иначе рекурсивная рассылка переполнит стек.

Событие синхронное: обработчики выполняются в том же потоке,
а `emit()` возвращается после их завершения. Здесь нет очереди,
фонового потока или защиты от одновременного доступа из разных потоков.
Сам `Event` должен существовать до завершения всех своих `emit()`;
обработчик не должен уничтожать событие. Копирование и перемещение события
запрещены, чтобы его идентичность и связь с ID оставались однозначными.

Цена простоты: создание записи выделяет память, а каждый `emit()` строит
снимок размера O(n). Подписка и отписка выполняют поиск в дереве за O(log n),
помимо стоимости выделения памяти и разрушения обработчика.

## Проверка и запуск

Из корня проекта:

```bash
cmake -S . -B build
cmake --build build --target cpp11_event_examples cpp11_event_checks
./build/c++11/functional/cpp11_event_examples
./build/c++11/functional/cpp11_event_checks
```

Ожидаемый вывод демонстрации:

```text
log: 2
log: 3
total: 5
after log unsubscribe: 9
after all unsubscribe: 9
once: 7
```

[Проверки](event_checks.cpp) покрывают изменение подписок внутри рассылки,
самоотписку, сохранение состояния `mutable`-лямбды, повторную отписку,
пустой обработчик, вложенный вызов и исключение из обработчика.

Без CMake можно собрать каждую программу отдельно:

```bash
c++ -std=c++11 -Wall -Wextra -Wpedantic c++11/functional/event_examples.cpp -o /tmp/event_examples
/tmp/event_examples
```

## Практика и развитие

1. Добавь третьего подписчика: журнал должен получить 2, 3 и 4,
   счётчик — только 2 и 3. Сними каждую подписку по её ID.
2. Создай одноразовый обработчик с самоотпиской без подсматривания в пример.
3. Проверь подписку нового обработчика внутри `emit()`: какой вызов он получит первым?
4. Сделай `Event` шаблонным по типу одного аргумента и передай событие с текстом.
5. Следующее улучшение — объект соединения с автоматической отпиской в деструкторе
   (RAII). Продумай, как он узнает, что событие уже уничтожено;
   простого сырого указателя на `Event` для произвольного порядка разрушения мало.
